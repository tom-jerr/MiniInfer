# MiniInfer 整体框架设计（基于当前代码实现）

## 1. 目标与范围

本文档基于当前仓库实现，描述 MiniInfer 在单机单进程模式下的推理框架设计，重点覆盖：

- 组件关系：Tokenizer / Scheduler / KVCacheManager / ModelRunner / Detokenizer
- 调度核心数据结构：`Req`、`ScheduledBatch`、`ForwardBatch`
- KV Cache 子系统：`CacheStorage`、`PagedTokenAllocator`、`RequestPool`、`RadixCache`
- Paged Attention（FlashAttention2 后端）实现方式
- Prefill / Decode / Mixed（chunked prefill）完整执行细节
- 请求完成、收缩（retract）、释放与 radix cache 回写流程

主要代码入口：

- `miniinfer/engine/llm_engine.py`
- `miniinfer/scheduler/scheduler.py`
- `miniinfer/scheduler/scheduler_batch.py`
- `miniinfer/kvcache/kv_cache_manager.py`
- `miniinfer/kvcache/memory_pool.py`
- `miniinfer/kvcache/radix_cache.py`
- `miniinfer/layers/attention_backend/flashattention_backend.py`
- `miniinfer/engine/model_runner.py`
- `miniinfer/models/fused_qwen2.py`

## 2. 运行架构

### 2.1 单进程主路径（当前默认）

`LLMEngine._init_single_process_mode()` 中，组件初始化顺序如下：

1. 创建 `ModelRunner` 并加载模型权重
2. 基于当前显存状态计算 `max_total_tokens`
3. 初始化 `KVCacheManager`
4. 将 `kv_cache_mgr` 注入 `ModelRunner`，初始化 `FlashAttention2Backend`
5. 初始化 `AutoTokenizer` 和 `IncrementalDecoder`
6. 初始化 `Scheduler`
7. 可选初始化 `CudaGraphRunner`（仅 decode）

一次 `engine.step()` 的执行链：

1. `Scheduler.schedule()` 产出 batch
2. `ForwardBatch.init_new()` 将调度元数据转换为前向元数据
3. `ModelRunner.forward()` 执行模型推理
4. `ModelRunner.sample()` 采样下一 token
5. `LLMEngine._process_step_result()` 增量解码并处理完成/释放

### 2.2 多进程模式现状

仓库中 `TokenizerWorker / SchedulerWorker / DetokenizerWorker` 代码目前为注释状态，主逻辑仍以单进程实现为主。设计上是 Tokenizer/Scheduler/Detokenizer 解耦，但当前可运行路径是单进程。

## 3. 核心数据结构

## 3.1 `Req`（请求生命周期对象）

定义位于 `scheduler_batch.py`。

### 输入与生成

- `origin_input_ids`：原始 prompt token
- `output_ids`：已生成 token
- `fill_ids`：`origin_input_ids + output_ids`，用于 prefill/chunked 场景

### 采样参数

- `sampling_params`（原始参数）
- `temperature / top_k / top_p / max_tokens / ignore_eos`

### 结束态

- `finished`、`finished_reason`
- `is_retracted`、`ever_retracted`（decode OOM 收缩后回队）

### KV/前缀相关

- `req_pool_idx`：RequestPool 槽位
- `prefix_indices`：命中 radix cache 的 KV 下标
- `cache_protected_len`：受保护前缀长度（锁住，不可驱逐/释放）
- `last_node`：前缀命中到的 radix 节点，用于 lock/unlock
- `extend_input_len`：本轮需要新分配 KV 的 token 数

### chunked prefill 相关

- `is_chunked`：是否是未完成的分块 prefill 请求
- `chunked_prefill_len`：已经处理到的长度，用于后续计算 `fill_ids`
- `total_input_len`：原始输入总长度


## 3.2 `ScheduledBatch`（调度结果）

Scheduler 的输出，表示一次要执行的批次。

- `reqs`：本批请求对象列表
- `forward_mode`：`EXTEND / DECODE / MIXED / IDLE`
- `input_ids`：送模型的 token（extend 为拼接后的新 token，decode 为每个请求最后 token）
- `req_pool_indices`：每个请求在 RequestPool 的行号
- `out_cache_loc`：本轮新 token 写 KV 的物理位置
- `seq_lens` / `seq_lens_cpu`：每请求当前总长度（GPU/CPU 双份）
- `prefix_lens`：每请求命中的 prefix 长度
- `extend_lens`：每请求本轮真正 forward 的 token 数
- `decoding_reqs`：mixed batch 中 decode 请求子集


## 3.3 `ForwardBatch`（模型前向输入）

`ForwardBatch.init_new(batch, attn_backend)` 负责构造。

- 复制 `input_ids / req_pool_indices / out_cache_loc / seq_lens`
- 绑定 `attn_backend`
- 构造 `positions`：
  - extend/mixed：按 `prefix_len .. prefix_len+extend_len-1` 展开
  - decode：`seq_lens - 1`
- 记录 `extend_prefix_lens(_cpu)`、`extend_seq_lens(_cpu)` 供注意力元数据、logits 裁剪使用，尽可能避免 CPU-GPU sync

## 4. Scheduler 设计

## 4.1 队列与状态

- `waiting_queue`：新请求等待 prefill
- `running_batch.reqs`：已进入 decode 的活动请求
- `chunking_reqs`：上一轮被截断、等待继续 prefill 的请求
- `finished_reqs`：完成请求

调度优先级：默认先尝试 prefill/mixed，失败后回退 decode。

## 4.2 PrefillAdder 预算模型

`PrefillAdder` 用于控制 prefill 是否可加请求：

- 输入：`available_kv_tokens`、`running_reqs`、`new_token_ratio`
- 为每个 running req 预留 decode 空间：
  - `reserve = min(remaining_max_tokens, CLIP=1024) * new_token_ratio`
- 所有预算按 `page_size` 对齐
- 支持 chunked prefill：空间不足时按页截断为 chunk，而不是直接拒绝

## 4.3 构造 prefill / mixed batch

`Scheduler._get_new_batch_prefill()`：

1. 先处理 `chunking_reqs` 的续块
2. 再遍历 `waiting_queue`，对每个 req 调 `kv_cache_mgr.prefix_for_waiting_req(req)`
3. `PrefillAdder.try_add_prefill(req)` 决定接受、拒绝或截断
4. 若开启 chunked prefill 且存在 running decode 请求，构建 mixed batch：
   - 新请求作为 extend
   - decode 请求视为 `extend_len=1`
5. 调 `kv_cache_mgr.prepare_for_mixed(batch, extend_reqs, decode_reqs)` 分配内存并写映射

## 4.4 构造 decode batch

`Scheduler._get_decode_batch()`：
实际上尽可能使用软限制来避免 retract 频繁发生，同时通过硬限制保证不 OOM：
1. `check_decode_mem()` 估算下一步是否需要新 page
2. 内存不足则从 batch 尾部 retract：
   - `release_request(req, is_insert=True)`
   - 请求状态重置后塞回 `waiting_queue` 头部
3. retract 连续发生时上调 `new_token_ratio`，成功多轮后下调
4. `kv_cache_mgr.prepare_for_decode(running_batch)` 分配每请求 1 个 token 的 KV 位置

## 5. KVCacheManager 设计

`KVCacheManager` 由 Scheduler 持有，负责请求到物理 KV 的全生命周期。

组件组成：

- `MHAKVCacheStorage`：每层 K/V 物理张量
- `PagedTokenAllocator`：按 page 分配 token 位置
- `RequestPool`：`req_idx -> token_pos -> kv_loc` 映射
- `RadixCache`：前缀命中、共享与驱逐

## 5.1 容量计算

在 `LLMEngine` 中，先加载模型再计算 `max_total_tokens`：

1. 读取 `torch.cuda.mem_get_info()` 当前显存
2. 计算每 token KV 字节：
   - `2 * num_layers * num_kv_heads * head_dim * dtype_size`
3. 预留约 20% 给激活和临时内存
4. 推导 token 上限并对齐 `page_size`

该上限直接决定 `KVCacheManager(size=...)`，后续 `free_pages`、KV buffer 都以此上限初始化。

## 5.2 Prefill 分配（prepare_for_extend）

对每个 req：

1. 计算 `fill_ids`，从 radix 匹配 `prefix_indices`
2. 分配 `req_pool_idx`
3. 若物理空闲不足且启用 prefix cache，先执行 `radix.evict(...)`
4. `alloc_pages_extend(...)` 返回本次新 token 的 `out_cache_loc`
5. 通过 Triton kernel `write_cache_indices(...)` 将：
   - prefix 旧索引
   - 新分配索引
   写入 `request_pool.req_to_token`

注意：每层共享同一组 `kv_loc` 索引，模型各层都往这些位置写本层的 K/V。

## 5.3 Mixed 分配（prepare_for_mixed）

- Extend 部分：同 prefill 路径，分配新 req_pool 槽位
- Decode 部分：复用已有 `req_pool_idx`，仅分配 1 个新 `kv_loc`
- 合并 `input_ids / seq_lens / prefix_lens / extend_lens / out_cache_loc`

这样混合批次可统一走 extend attention kernel。

## 5.4 Decode 分配（prepare_for_decode）

1. `input_ids` 取每个请求 `output_ids[-1]`
2. 读取每个请求上一个 token 的 `last_loc`
3. `alloc_pages_decode(...)` 分配当前步位置
4. `seq_lens += 1`
5. 回写 `req_to_token[req_pool_idx, new_pos] = out_cache_loc`

## 5.5 释放与回写

### 完成请求

`update_finished_req_radix_cache(req)`：

1. 从 RequestPool 读出该请求全部 `kv_indices`
2. 插入 radix（按 page 对齐）
3. 释放重复区间和尾部未对齐区间
4. 释放 request_pool 槽位
5. `dec_lock_ref(req.last_node)` 解除前缀保护

### retract/abort

`release_request(req, is_insert=True)` 与上面相同逻辑，但用于中途收缩。

### chunked prefill 中间态

`update_unfinished_req_radix_cache(req)` 只更新 radix 命中和锁，不立即释放 allocator 中 token，避免重复释放。随后上层流程会释放 request_pool 槽位并让请求继续下一 chunk。

## 6. 内存子系统细节

## 6.1 CacheStorage

`MHAKVCacheStorage` 分配：

- `k_buffer[layer]`: `(size + page_size, num_heads, head_dim)`
- `v_buffer[layer]`: 同上

`+ page_size` 主要用于 padding，padding 得到的 kv 我们并不需要，所以写入 page 0，我们不会访问这个 page 0。

## 6.2 PagedTokenAllocator

关键约束：

- page 粒度管理，`page 0` 保留不用
- `free_pages` 初始为 `[1..num_pages]`
- `available_size = len(free_pages) * page_size`

### Extend 分配（Triton kernel）

按请求分 3 段处理：

1. 先填满前一页剩余空间
2. 分配若干整页
3. 分配最后不足一页的尾部

### Decode 分配

- 若 `last_loc` 仍在页内，则 `last_loc + 1`
- 若跨页，则取新页页首

## 6.3 RequestPool

`req_to_token[max_requests, max_context_len]` 保存每个请求每个 token 对应的物理 `kv_loc`。

这是调度态和注意力态之间最关键的桥接结构。

---

## 7. RadixCache 设计（页对齐版本）

`RadixCache` 节点字段：`key`（token 序列）、`value`（kv indices）、`children`、`lock_ref`、`last_access_time`。

## 7.1 匹配和插入

- `page_size=1`：逐 token 匹配
- `page_size>1`：按 page chunk 匹配，key/value 先向下对齐到 page 倍数

因此当 `page_size=16/256` 时，尾部不足一页的 token 不会进入 radix，可避免跨页悬挂引用。

## 7.2 锁与可驱逐性

- 命中前缀后 `inc_lock_ref(last_node)`，请求结束后 `dec_lock_ref`
- 仅 `lock_ref==0` 的叶子可驱逐
- `evictable_size()` 还会被当前物理已用容量上限约束，防止逻辑可驱逐数虚高

## 7.3 驱逐策略

- 基于 `last_access_time` 的近似 LRU
- 逐叶驱逐并释放 allocator 页面
- 驱逐后删除叶节点，必要时向上回收空父节点

## 8. Paged Attention（FlashAttention2）实现

## 8.1 元数据构建

`FlashAttention2Backend.init_forward_metadata(forward_batch)`：

- `cache_seqlens_int32`
- `max_seq_len_q / max_seq_len_k`
- `cu_seqlens_q / cu_seqlens_k`
- `block_table`

`block_table` 构建方式：

1. 从 RequestPool 取 `kv_locs = req_to_token[reqs, :max_seq_len_k]`
2. 每页取第一个 token：`kv_locs[:, ::page_size]`
3. 转块号：`block_id = kv_loc // page_size`

这就是 paged attention 所需的“逻辑序列 -> 物理页块”映射。

## 8.2 Extend 路径

- 先将新 token 的 K/V 写入 `out_cache_loc`
- 若命中 prefix cache，`q/k/v` 只覆盖新 token，但 attention 的 `k` 长度是全序列长度
- 因此需要从 paged KV cache 按 `kv_locs` 回收完整 K/V，再调用 `flash_attn_varlen_func`

## 8.3 Decode 路径

- 每个请求 `seqlen_q=1`
- 将缓存 reshape 为 `[num_pages, page_size, nheads, head_dim]`
- 调 `flash_attn_with_kvcache`，输入 `block_table + cache_seqlens`

## 9. 模型推理与采样

## 9.1 模型前向

`Qwen2Attention.forward()`：

1. `qkv_proj`
2. `RoPE(q, k)`
3. `self.attn(q, k, v, forward_batch)`
4. `o_proj`

`AttentionImpl.forward()` 不直接算 attention，而是委托 `forward_batch.attn_backend.forward(...)`，实现模型层与后端解耦。

## 9.2 融合算子（Add + RMSNorm）

`add_rms_norm_forward` 返回 `(normalized_output, new_residual)`：

- `hidden_states = rmsnorm(x + residual)`（给 MLP）
- `residual = x + residual`（给后续残差链）

当前实现已经按这个顺序返回。

## 9.3 采样

- extend/mixed：logits 是 `[total_extend_tokens, vocab]`，先按 `extend_lens` 切出每个请求最后一个 token 的 logits
- decode：logits 已是 `[batch, vocab]`
- `Sampler` 按每请求 `temperature/top_k/top_p` 采样

关于约束解码：当前 `SamplingBatchInfo` 预留了 `vocab_mask/apply_mask_func` 字段，但主路径尚未完整接入约束 mask 逻辑。若要支持 grammar/vocab 约束，应在 softmax 之前对 logits 做 mask。

---

## 10. Prefill / Decode / Finish 端到端时序

## 10.1 Prefill（含 prefix 复用）

1. 请求入 `waiting_queue`
2. `prefix_for_waiting_req` 命中 radix，得到 `prefix_indices`
3. Scheduler 按预算组批（可 chunked）
4. `prepare_for_extend/mixed` 分配 `req_pool_idx + out_cache_loc`
5. 模型前向写 K/V 到 `out_cache_loc`
6. sample 产生下一个 token

## 10.2 Decode

1. 请求进入 `running_batch`
2. 每步先做 decode 内存检查，不足则 retract
3. `prepare_for_decode` 为每请求分配 1 个新 `kv_loc`
4. FA2 decode 读取 `block_table + cache_seqlens` 做注意力
5. sample 并增量 detokenize

## 10.3 完成与释放

1. 命中 EOS 或达到 `max_tokens`
2. `update_finished_req_radix_cache` 将页对齐前缀插入 radix
3. 释放可释放 KV page + request pool 槽位
4. 解除 radix lock

---

## 11. 现状与注意点

1. 调度主路径在 `LLMEngine.step()`，`Scheduler.run_batch()` 路径未被当前引擎主流程使用。
2. `_prepare_chunked_input_ids()` 目前是空实现，实际 input_ids 由 KV manager 的 prepare 阶段按 `fill_ids` 构建。
3. 多进程 Worker 目前是注释代码，属于后续扩展方向。
4. `Scheduler.get_budget_stats()` 中 `decode_waiting_ticks` 字段在当前类内未初始化，调用该接口需补齐该状态或移除字段。

---

## 12. 总结

MiniInfer 当前实现是一个典型的“调度驱动 KV 生命周期”的推理架构：

- Scheduler 负责批次形态与预算决策
- KVCacheManager 负责物理分配、逻辑映射与前缀共享
- PagedAttention 通过 `req_to_token -> block_table` 打通逻辑序列与物理页块
- Prefill/Decode 共享同一套缓存系统，在 mixed 模式下统一为 extend 计算

这套设计的核心价值是：在有限显存下，通过 page 对齐分配、radix 前缀复用和连续批调度，实现高吞吐和可扩展的在线生成。
